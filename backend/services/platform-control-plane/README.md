# Platform Control Plane

## Purpose
Own SaaS-level tenant registry and lifecycle, verified domain mappings, plan/entitlement metadata, provisioning orchestration records and database/secret references. This service does not own tenant commerce data.

## Increment A: local foundation

The implementation exposes `GET /health` (process liveness, independent of PostgreSQL) and `GET /ready` (a `SELECT 1` using the runtime identity; 503 on database failure). `/docs` exposes the generated OpenAPI documentation. The tenant registry defines create, list, get and deletion-request operations. Nested domain routes register, list and locally verify tenant hostnames. These routes require a signed OIDC bearer token with the configured issuer, `control-api` audience and `platform-operator` realm role. Missing/invalid authentication returns 401 and missing authorization returns 403.

From the repository root, with Docker Desktop running:

```powershell
python .\scripts\bootstrap_identity.py
docker compose --env-file .env -f .\infra\local\compose.yaml --profile identity --profile platform-control --profile platform-console up -d --build
docker compose --env-file .env -f .\infra\local\compose.yaml --profile identity --profile platform-control --profile platform-console ps
Invoke-RestMethod http://127.0.0.1:8000/health
Invoke-RestMethod http://127.0.0.1:8000/ready
```

The API container receives only `PLATFORM_CONTROL_RUNTIME_PASSWORD`; it does not receive the bootstrap, migrator, worker, provisioner, Keycloak administrator or operator passwords. Runtime OIDC configuration consists of issuer, audience and JWKS URL. The migration process separately requires `DB_HOST` and `PLATFORM_CONTROL_MIGRATOR_PASSWORD`. It never uses API credentials.

### Local tenant-domain preview

An authenticated platform operator registers a unique `localhost` or `*.localhost` hostname and
assigns its purpose as `STOREFRONT` or `TENANT_ADMIN`. The local verification adapter can verify
these reserved development names without a DNS provider or environment allowlist. Visit the
application through its hostname (and local development port); `/_local/tenant` resolves a
verified database mapping to its tenant and purpose. Unknown, unverified and deletion-requested
tenants return 404. A browser Host header is still not authorization and must never select a
tenant database by itself. This preview route is disabled in production; production will require
trusted ingress plus a DNS ownership verification adapter.

To run on the host from this service directory, first securely populate the required environment variables from the ignored root `.env` and set `DB_HOST=127.0.0.1`, then run `uv sync --locked` and `uv run uvicorn platform_control_plane.main:app --host 127.0.0.1 --no-access-log`. Run migrations separately with `uv run alembic upgrade head` using migrator settings only after explicit owner approval. Revision `001_tenant_registry` creates three platform-metadata tables; future revisions belong to this service alone.

Run `uv lock --check`, `uv run ruff check src tests migrations`, `uv run ruff format --check src tests migrations`, `uv run mypy src`, and `uv run pytest`. Integration tests require `RUN_DB_INTEGRATION=1`, a running local database and the runtime settings. Tests must never use the bootstrap administrator in the API.

The source package contains API routes, Pydantic configuration and safe event logging in `core/`, engine and sessions in `database/`, FastAPI dependencies, and response schemas. `main.py` starts and disposes the engine. `migrations/` configures Alembic with the separate migrator. The Dockerfile uses a non-root user and excludes local secrets from its build context. Request IDs are generated by the server, and log events contain no request bodies, credentials, SQL, or exception strings.

Registry behavior: `POST` requires `Idempotency-Key` (1-128 characters), a `display_name`
and a validated `initial_owner_email`; it creates an opaque UUID with status `PENDING`, records
an audit event atomically with the authenticated OIDC issuer/subject, returns 201, returns 200 for
an identical retry, and returns 409 for a reused key with different content. The normalized owner
contact is onboarding metadata for the Identity bootstrap workflow; the Control Plane does not
create credentials or memberships. `PUT /api/v1/tenants/{tenant_id}/owner-contact` supports an
audited correction for existing tenants without recording the email in audit-event text. GET list
uses `limit` (1-100, default 20) and `offset` (0-10000); GET by ID returns 404 if absent. DELETE
performs an idempotent, audited transition to `DELETION_REQUESTED`; it never erases tenant
databases or bypasses retention/offboarding review.

Local domain behavior: `POST /api/v1/tenants/{tenant_id}/domains` registers a normalized globally
unique `localhost` or `*.localhost` hostname in `PENDING_VERIFICATION`, with one `STOREFRONT` and
one `TENANT_ADMIN` hostname permitted per tenant. The local verify endpoint changes the reserved
hostname to `VERIFIED` without public DNS. Pending, provisioning, failed and active tenants may
manage domains; deletion-requested tenants fail closed. Provisioning specifically requires the
verified Storefront domain. Production public domains and provider verification remain separate.

Limitations: local Keycloak uses development mode and one broad operator role. Production MFA, granular super-admin/support permissions, session revocation policy, rate limiting, TLS and reviewed identity-provider configuration are not implemented. Domain verification, lifecycle transitions and provisioning remain later Phase 1B increments. Each owned table is explicitly restricted, and Alembic revokes runtime access to its version table after online migrations. Local passwords are ignored environment values and production requires a reviewed secret provider. Image tags are version-pinned but not digest-pinned. The service is not approved for production.

## Data ownership
Singleton `platform_control` database only. Never store tenant products, customer profiles, carts, inventory, orders, payment transactions or provider secrets in plaintext here. Store opaque secret references only.

## Process boundaries
- HTTP API: tenant registry/domain/lifecycle operations, least-privilege `platform_control_runtime` DB role.
- Migration runner: this service's Alembic migrations, `platform_control_migrator` role.
- Provisioning worker: reads/writes only authorized provisioning-job rows using `platform_control_worker`; database/role creation uses a separate privileged credential supplied only to that isolated worker. No public route can call arbitrary SQL/provisioning commands.
- The worker creates one tenant database, service schemas, roles and secret references. It MUST NOT run Catalogue/Inventory/Orders or any other owning-service migrations. Each owning service runs its own schema migration job using its own migrator.

## First implementation increments
1. Health/readiness and validated configuration.
2. Control-plane schema and migrations.
3. Tenant registry with lifecycle state machine and audit metadata.
4. Domain registration/verification state using a deterministic local test adapter only.
5. Durable provisioning job state and worker boundary.
6. Two-tenant provisioning proof and negative credential tests.

## Identity & Access infrastructure boundary

The Control Plane can provision the `identity_access` service boundary for a tenant. It creates
only the opaque tenant database metadata, dedicated `identity` schema, runtime/migrator roles and
local secret reference. It does not create Keycloak users, invitations, staff memberships or
Identity tables, and it never runs Identity migrations. Active tenants may enable this additional
service without regressing their lifecycle status; new tenants continue through `PROVISIONING`.
It stores the initial owner contact needed to request the first Identity invitation, but it never
stores an owner password, Keycloak credential or tenant membership.

## Security invariants
- Tenant context derived from trusted ingress + verified domain lookup.
- Browser-supplied tenant IDs are never database-routing authority.
- Verify signed internal context issuer, audience, expiry, key ID/signature and tenant lifecycle.
- Tenant DB access denied by default; revoke `CONNECT`/`TEMPORARY` from `PUBLIC`.
- Runtime role cannot create databases/roles or apply DDL. Provisioner credential is never loaded by the HTTP API.
- Provisioning is idempotent, bounded, auditable and recoverable.
